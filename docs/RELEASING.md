# 校验、三方审核与发布

仓库目前使用 `.github/workflows/validate.yml` 校验每次 push / PR；正式发布由维护者使用 GitHub CLI 完成。版本采用递增 `vMAJOR.MINOR.PATCH` 标签，与模板中的 `SCRIPT_VERSION` 对齐，不覆盖已有标签或资产。

1. 保存工作区基线，只暂存本次明确文件。修改模板或生成器后执行 `python clash.py`，再执行 README 的全部检查及 `git diff --check`。
2. 为任务 A（兼容）、B（示例）、C（部署）、D（格式一致性）准备同一份脱敏证据包，包括基线、完整差异、相关源码、文档、示例、生成物、测试结果和拟发布说明，记录输入 SHA256。
3. GPT、MiniMax、GLM 各自独立检查正确性、策略语义、兼容性、隐私边界和测试充分性。独立阶段不提供同伴意见。记录真实渠道、响应模型、请求或会话标识、逐任务意见及明确结论；调用失败不能记为通过。
4. 三方各自交叉复核其他两方全部意见。修复后重测并重新审核受影响部分；保留原意见和修复证据。只有三方都明确通过且无未解决阻断才能关闭任务，不用多数票代替解决争议。
5. 形成本地提交后，三方再次审核该确切 SHA 的整体差异及全部发布材料。最终审核记录存放在忽略的 `output/` 中并作为 Release 附件，不再为记录签核而修改被审核提交。后续实质修改必须重新签核。
6. 三方最终通过后，重新核实远端、目标分支及版本未被占用，正常推送，不强推。若需 PR，遵循分支保护；合并产生的新 SHA 也需最终签核。等待对应 SHA 的全部 GitHub CI 成功，失败先修复并重走受影响审核。
7. 创建指向审核通过 SHA 的版本标签，并以该标签创建正式 GitHub Release（非 draft、非 prerelease）。发布说明使用已审核版本文档，附 `override.js`、`server-policy.yaml`、`server-provider.example.yaml`、脱敏 `review-records.json` 和 `SHA256SUMS`。
8. 使用未认证的公开下载复核附件摘要；确认标签提交、审核 SHA、CI、生成物字节、说明及无秘密扫描一致。记录 CI 和公开 Release 链接。

审核日志不得包含鉴权头、API 密钥、真实订阅、节点、listener 凭据、完整服务器配置或原始连接日志。发布摘要覆盖除 `SHA256SUMS` 自身外的上述附件。发布材料必须明确区分源码核对、离线测试和生产运行验证。
